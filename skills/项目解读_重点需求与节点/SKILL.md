# 项目解读_重点需求与节点

## 一、这个技能解决什么

售前调研后最常见的卡点是：**资料一大堆，却提炼不出能直接进方案的重点**。本技能把"读资料 → 提炼三部分 → 套模板出 PPT"固化成一条可复现的流程，保证每次产出结构一致、内容可追溯、约束统一（待确认标注、可检验判定标准、行业缩写保留、WPS 占用处理）。

交付物固定为 6 页 PPT：
```
封面 → 一、重点需求 → 二、主要流程描述 → 三、重要节点描述 → 四、待确认事项 → 五、结论与建议
```

## 二、触发条件

**命中任一即触发：**
- "解读项目资料 / 梳理项目 / 提炼重点需求 / 提炼关键节点"
- "输出重点需求解析 / 生成重点需求 PPT"
- "把调研资料整理成重点需求与节点"
- "按生产制程顺序梳理流程、标管控节点"

**不触发（移交其他技能）：**
- 已有 PPT 只想改样式/合并/美化 → `摩尔多页PPT合并`、`more-jpg-to-ppt`
- 要的是"需求 → 改善方向 → 依据"完整推导链 → `摩尔方案-需求与改善方向`
- 要的是完整 MES 方案（版式设计、图标、栅格） → `摩尔结构化方案编写`
- 只要一份调研计划表格 → `tencent-docs-sheet-generation`

## 三、输入参数

| 参数 | 必填 | 说明 | 缺省处理 |
|---|---|---|---|
| `source_path` | 是 | 项目资料文件夹（含 docx/txt/xlsx/图片/音视频） | 无 → 先索取，不得编造 |
| `template` | 否 | 摩尔方案模板 `.potx` 路径，默认 `E:\02跟进项目\摩尔方案模板.potx` | 不存在 → 报告并询问 |
| `client` | 是 | 客户简称（用于标题与文件名，如"旺达电子"） | 从路径/资料推断并显式回告 |
| `date` | 否 | 归档日期前缀 `YYYYMMDD` | 默认当天 |
| `depth` | 否 | `standard`（默认，需求 7–10 条）/ `deep`（每条附根因+数据基线） | standard |
| `unknown_policy` | 否 | `mark`（默认，标"待确认"）/ `ask`（致命缺失才追问） | mark |

## 四、执行流程（六阶段 + 依赖关系）

```
        ┌─ S0.1 确认输入(资料/模板/客户/日期)
S0 准备 ─┤
        └─ S0.2 搭建隔离 venv(python-pptx/openpyxl/python-docx)  ← 一次性，可复用

S1 资料解析 ── S1.1 列举+分组 → S1.2 读核心源文档 → S1.3 抽工艺/节点/基线 → S1.4 提炼三部分
S2 模板解析 ── S2.1 potx→pptx 修 content-type → S2.2 解析版式/占位符 → S2.3 记录主题色/字体
        （S1 与 S2 可并行，均只依赖 S0）

S3 渲染生成 ── 依赖 S1(内容) ∩ S2(版式)：复制模板→清示例页→按6版式填内容(enumerate自动编号)
S4 校验     ── 依赖 S3：包完整性 + 几何溢出 + 内容(无P0/P1/P2·编号·缩写·待确认)
S5 归档     ── 依赖 S4 通过：命名落盘 + WPS 锁检测(占用则递增版本，不覆盖/不杀进程)
```

**顺序与依赖（MECE）：**
- **S0 →（S1 ∥ S2）**：输入确认后，资料解析与模板解析互不依赖，可并行。
- **S1 内部**：S1.1→S1.2→S1.3→S1.4 必须顺序；S1.2 多份文档可并发读取。
- **S2 内部**：S2.1→S2.2→S2.3 顺序（先能打开才能解析）。
- **S3 强依赖 S1∩S2**：内容与版式都齐了才能渲染；任缺其一都不能开始。
- **S4 依赖 S3**；**S5 依赖 S4 通过**。

> 详细步骤、判断标准与常见错误见 `references/process_flow.md`。

## 五、输出格式（固定结构与章节顺序）

**三部分内容（写入 PPT 与可附 .md 说明）：**

1. **重点需求（7–10 条）**：条列式，每条带「标题 + 可检验的判定/量化说明」。排序维度：`客户关注度 × 业务价值 × 落地可行性`。**不使用 P0/P1/P2 标注**（如需优先级，用文字理由说明）。编号由脚本 `enumerate` 自动生成（增删条目自动重排）。
2. **主要流程描述**：按生产制程顺序梳理为节点流（来料检验 IQC → SMT → DIP → 组装 → 老化测试 → 包装 → 出货），每节点写"动作/约束"。
3. **重要节点描述**：表格三列 = `管控节点 | 管控内容 | 判定标准`，每个节点必须回答"在哪卡"和"靠什么判断"。

**PPT 页结构（6 页）：** 封面 / 一、重点需求 / 二、主要流程描述 / 三、重要节点描述 / 四、待确认事项 / 五、结论与建议。

## 六、约束边界

**必须：**
- 凡资料无依据的数字，一律标 **「待确认」**，禁止估算当事实。
- 每条改善/管控方向必须**可检验、可量化或有明确判定标准**，禁止"加强管理/提高意识"类空泛表述。
- 行业缩写（SMT / BOM / ERP / FIFO / ECN / Andon / IQC / SPC / CPK …）**保留原文**。
- 副标题与需求条目须**分段**，避免粘连在同一段落。
- 交付前必须做校验并逐项报告。

**禁止：**
- ❌ 编造规模数据（产线数、产能、人员、面积）。
- ❌ 用 P0/P1/P2 等无理由优先级标签代替"显式理由"。
- ❌ 未做校验（包完整性 + 溢出扫描）就宣称完成。
- ❌ 源文件被 WPS 占用时覆盖/强删/结束用户进程。

## 七、校验清单（全过才算完成）

1. `zipfile.testzip()` 通过，全部 xml 良构。
2. 无文字/图形溢出（形状均在 13.33×7.5″ 画布内）。
3. 重点需求编号连续、无 P0/P1/P2、无 ①。
4. 缩写保留、待确认项未藏入正文。
5. 副标题与首条需求不粘连。
6. 文件名符合 `YYYYMMDD_客户简称_重点需求.pptx` 且落在源资料同目录。
7. 若 `~$` 锁文件存在 → 另存 `_vN` 版本，并在说明里交代"关闭后可覆盖回原名"。

## 八、版本命名与归档

```
YYYYMMDD_{客户简称}_重点需求.pptx        ← 首个交付版
YYYYMMDD_{客户简称}_重点需求_v2.pptx     ← 修订版（WPS 占用或二次修订）
YYYYMMDD_{客户简称}_依据说明与待确认清单.md ← 同名说明（可选，列依据与待确认）
```

## 九、配套脚本与用法

脚本目录 `scripts/`：
- `build_deck.py` —— **渲染主脚本（可复用骨架）**。读取 `content.json` + 模板 `.potx`，自动完成 potx→pptx 修正、清示例页、按 6 版式渲染、`enumerate` 自动编号、WPS 锁递增、包完整性+溢出校验。
- `inspect_template.py` —— 解析任意 `.potx/.pptx` 的版式名称、占位符、主题色/字体，便于换模板时核对。
- `verify_deck.py` —— 对生成后的 pptx 做完整性 + 溢出 + 内容抽查。

**最小执行命令（隔离 venv）：**
```bash
PY="C:/Users/majunpeng/.workbuddy/binaries/python/envs/default/Scripts/python.exe"
# 1) 写 content.json（由 AI 据资料提炼，参考 assets/example_content_wangda.json）
# 2) 渲染
$PY scripts/build_deck.py --tpl "E:\02跟进项目\摩尔方案模板.potx" --content content.json --out 输出.pptx
# 3) 校验
$PY scripts/verify_deck.py 输出.pptx
```

**content.json 结构（详见 assets/example_content_wangda.json）：**
```json
{
  "meta": {"client":"旺达电子","date":"20261009","industry":"...",
           "cover_subtitle":"...","cover_date_line":"...","req_subtitle":"..."},
  "requirements": [{"title":"...","desc":"..."}],
  "process": {"subtitle":"...","stages":[{"name":"...","acts":"行1\n行2"}],"callouts":[{"title":"...","desc":"..."}]},
  "nodes": {"subtitle":"...","rows":[{"node":"...","control":"...","criteria":"..."}]},
  "todos": ["... → 待确认"],
  "conclusion": [{"head":"结论","text":"..."}]
}
```
