# 摩尔调研报告整理

**一句话定位**：把一次客户现场调研的零散资料，整理成一份可直接对客户交付、按摩尔范本五章成稿、事实零编造、看不到任何内部作业痕迹的 Word 调研报告。

**唯一目标成果基线**：`E:/02跟进项目/上海-上海爱欧光学MES项目-激光器-20261104/售前资料/上海爱欧光学 MES 系统建设现场调研报告_20261105_修订版.docx`（下称「基线件」）。所有结构、措辞、命名、验收口径以基线件为准；逐项对应关系见 `references/目标成果基线.md`。基线件只作规范参照，**不得把其中的客户名、数字、系统名、日期抄进新报告**。

**最高铁律**：报告是给客户看的正式交付件。任何暴露「我们是怎么拿到资料、怎么整理、怎么应要求改稿」的字句一律不写进文档；编写规则只存在于本技能，不进正文。

---

## 一、触发条件

### 必触发
- 用户提供调研资料目录/文件 + 范本 `.docx`，要求「整理成 / 生成 / 按范本成稿」现场调研报告。
- 用户要求把会议记录、访谈记录、纪要、转写稿转成按摩尔五章结构的调研报告。
- 对已有调研报告提出整理类修改：去掉 `[E-xxx]` 类标注、去掉资料来源字眼、删除附录、精简调研时间、删除元说明句、出修订版、按基线件复刻口径。
- 用户要求复现「上次那份调研报告」的结构与标准。

### 不触发（改走其他技能）
| 场景 | 去向 |
|---|---|
| 把调研结论做成汇报 PPT / 专题方案 | `摩尔结构化方案编写` |
| 多页方案 PPT 合并套模板 | `more-jpg-to-ppt`、`摩尔多页PPT合并` |
| 图片转单页矢量 PPT | `more-jpg-to-ppt` |
| 纯多模态素材理解、错别字质检、约 200 字项目总结 | `mes-customer-research-report` |

### 与相邻技能的分工（避免口径冲突）
`mes-customer-research-report` 侧重素材解析与事后质检，可配合本技能做素材理解；但其「保留待确认标注」「输出项目总结」等口径**不得覆盖本技能**。凡涉及摩尔范本五章结构、表格字段、客户可见措辞、页脚与命名，**一律以本技能为准**。

## 二、适用资料范围

**适用行业与客户类型**：电子组装、高端装备、医疗器械、新能源电池、半导体、注塑、钣金、激光器/光学、新材料等离散制造客户的 MES/MOM 售前现场调研。

**适用的调研形态**：现场会议访谈 + 车间/仓库走访 + 系统现状摸底 + 供应商方案交流；覆盖计划 PMC、生产、工艺、品质、设备、仓库、IT 等部门。

**不适用的场景**：纯问卷统计报告、招标文件响应、技术方案书、验收报告、只做数据透视的表格加工——这些不套用五章调研报告骨架。

## 三、输入文件要求

| 类别 | 必需性 | 说明 |
|---|---|---|
| ① 调研资料 | **必需** | 至少一个资料目录或文件集；可为 `.docx` 访谈记录/纪要/转写稿、`.txt`、`.pdf`、现场照片、系统清单、Excel 台账。逐份读完再动笔，不可只读摘要。 |
| ② 范本 `.docx` | **必需** | 摩尔调研报告模板（本次为《摩尔调研报告模板.docx》）。仅取**章节骨架、表头字段、标题样式、页眉页脚结构**；范本中的示例数字、人名、产能、线体数量**一律禁用**。 |
| ③ 项目元数据 | **必需** | 客户简称（取项目目录名或用户指定，不擅自加「有限公司」）、调研日期、编制日期、版本号。 |
| ④ 目标成果基线 | 建议 | 需要「与上次一致」时显式提供基线文件路径；缺省用 `references/目标成果基线.md` 的结构指纹。 |

**资料缺失处理（零编造）**
- 数字、人名、系统正式名称、设备型号、具体日期：资料没有就写「本次资料未载明」，**不推算、不套范本、不凑表格行数**。
- 同一事实在资料里有多种口径（如 ERP 名称、上线时间、车间面积、车间名称）：并列写出并标「待确认」，同时列入表7 确认类待办，不擅自择一。
- 人名只按可确认的**岗位/团队**填写（如「摩尔元数 售前顾问组」「客户 采购经理」），不指派具体人名。
- 「本次资料未载明」属于证据状态标注，**不是占位符**；但不得叠加解释性元说明（见 §5.6）。

## 四、整理工作流

| Step | 动作 | 关键约束 |
|---|---|---|
| 0 | 建立任务清单（≥4 步），备份任何待改的已有文档 | 改前必备份到系统 Temp |
| 1 | 盘点资料与范本，用 `zipfile` 提取范本骨架（章节 + 表头 + 样式 + 页脚） | 记录范本表头字段原样，禁用范本示例数据 |
| 2 | 逐份通读调研资料，按部门抽取客观事实，建证据编号 `E-xxx` 台账 | **证据台账是内部工作底稿，只用于自查，不写进交付文档** |
| 3 | 按 §5 规则撰写正文 + 7 张主表 + 术语约定表 + 文末自检清单 | 结论先行、三段式、MECE、术语全称 |
| 4 | 生成 `.docx`：复用范本 `styles.xml`/`theme`，替换 `word/document.xml`，新增 `word/footer1.xml` 并同步 `[Content_Types].xml` 与 `document.xml.rels` | 见 §9 工程约束；页脚保留 PAGE 页码字段 |
| 5 | 执行客户可见性净化（§5.6）与命名/版本设置（§7） | 逐字扫描禁用词，含页脚与表格单元格 |
| 6 | 运行 `scripts/verify_report.py <docx>` 验收；全部 PASS 后清理中间文件并交付 | 有 FAIL 必须修到全绿；WARN 需说明 |

**修订既有报告时**：跳过 Step 1—4 的内容生成，按 §5.6 与 `references/客户可见性红线.md` 精确删除/替换，删除后必须清理遗留空格与孤立分隔符（如 `。 `、悬空 `/`），并同步修订文末自检清单里对已删内容的引用，避免自相矛盾。

## 五、报告整理规则

### 5.1 结论先行
- 正文（第一章之前）置「**调研结论摘要**」，**恰好 5 条**，每条为「结论 + 支撑事实」，不写 `[E-xxx]`。
- 每章开头一句「**本章结论：**…」；每个 2.x / 3.x / 4.x 子节开头一句「**结论：**…」或三段式的段首结论。
- 结论只归纳本次资料中已出现的事实，不引入外部行业基准数字。

### 5.2 零编造与证据口径
- 所有数字、人名、系统名、设备型号、日期只能来自本次调研资料与项目元数据。
- 内部可建 `E-xxx` 证据台账保证可回溯，但**交付文档正文、表格、结论、附录中一律不显示任何证据编号标注**，也**不输出「附：证据索引」章节/表格**。
- 「机制缺失 → 业务后果」类判断属于分析结论，允许写，但不得伪装成客户原话或捏造数量。

### 5.3 MECE 与三段式
- 第三章按部门独立成节，**3.1—3.11 共 11 个子节**，编号连续；同一事实只在一处陈述（**此规则只作编写约束，不得作为句子写进报告正文或自检清单**）。
- 跨部门的集成、时间、扩展、待确认事项归入 **3.10 项目范围与产能** 或 **3.11 IT 部门与基础设施**；车间级共性管控归入 **3.9 车间分组细化**。
- **3.9 的正式标题固定为「车间分组细化」**；正文、本章结论、自检清单中描述该节时须与标题一致，禁止混用「其它管理（总）」等模板遗留称谓。
- 每个部门子节固定「现状 / 需求 / 痛点」三段，每段**先一句结论再展开要点**：
  - **现状**：只写客观事实（谁、哪个环节、用什么工具、频率/数量）。
  - **需求**：写成可交付可验收的系统能力，含触发条件 / 卡控点 / 数据字段 / 输出结果；禁止「提升效率」「加强管控」类空话。
  - **痛点**：写成「缺少 X 机制 → 具体业务后果」；禁止形容词堆砌。

### 5.4 表格规则
- **7 张主表，表号 表1—表7 连续**；表头与字段**原样沿用范本**，行数按实际资料扩展，不凑数编行。
- 表1 项目基本信息 8 字段：项目名称 / 调研人 / 调研时间 / 调研方式 / 调研地点 / 访谈部门 / 调研方向 / 项目负责人。
- 表2 车间线体、表3 主要产品、表4 IT 系统现状与集成、表5 仓库现状、表6 车间/产线分组细化、表7 后续行动计划。
- 表7 **每行必须有责任人与预计完成时间**；无确切日期时用可核验的阶段锚点（如「基础方案审核通过后」），并显式标注「具体日期本次资料未载明」。
- 表格下方「注：」只写字段口径与待确认项，不写资料来源、不写「本报告不推算/不推断」类元说明。
- 术语约定表为**附录表，不编表号、不计入 7 张主表**，全文共 **8 张表**。

### 5.5 术语规则
- MES / MOM / WMS / QMS / IOT / ECN / ECR / SOP / Andon / SPC / OEE 统一写法，**首次出现给中文全称**；资料中的异写（ECN/ECM/DCN 等）统一为标准写法。
- 文末「附：术语约定（不编章号）」表 3 列：术语 | 中文全称 | 本报告用法；本次资料未出现的术语可列入并注明「后续方案引用时沿用本写法」。
- 完整术语表见 `references/报告结构规范.md`。

### 5.6 客户可见性红线（★ 本技能最关键约束）
以下字句**一律不得出现在交付文档的任何位置**（正文、表格单元格、表注、附录、自检清单、页脚）：

1. **资料来源 / 内部作业字眼**：录音、原文转写、听记、钉钉 AI 听记、纪要、源文件、时间码、发言人、两段录音、4 份源文件、资料基础、口述、复述。改为「现场亦称」「客户介绍」「现场调研确认的流向」「本次现场调研」等中性表述。
2. **证据编号标注**：`[E-xxx]` 及任何 `E-xxx` 形式的正文标注；「附：证据索引」整章（标题、说明段、索引表）。
3. **内部对话痕迹**：「按客户要求」「按要求」「本次修订」「上一版」等。
4. **元说明句**（本次逐条删过的精确字符串，见 `references/客户可见性红线.md`）：
   - 「参会人员姓名本次资料未载明，本报告不推断具体人名。」
   - 「（按项目资料夹命名；客户工商全称本次资料未载明）」
   - 「（园区政府提供整层空间，本期范围为其半层；具体门牌地址本次资料未载明）」
   - 「摩尔元数侧项目负责人本次资料未载明。」
   - 「本报告不据此推算产能。」
   - 「同一事实只在一处陈述。」
   - 页脚「依据：…」整段。
5. **供应商侧动作**：表1「调研方式」只写客户现场实际发生的调研动作（现场会议访谈 / 车间走访 + 走访范围），不写「供应商方案与行业案例演示」。
6. **调研时间过细**：写「YYYY 年 M 月 D 日」或「YYYY 年 M 月 D 日 总起止时段」，**不拆分会场分时段**（不写「MES 系统需求沟通会 15:38—16:54；工厂参观与产能上市规划交流 16:54—17:03」）。

**保留项（属业务事实，不得误删）**：「钉钉」作为客户在用系统 / 接口 / 分级预警；ERP「金蝶／云城」待确认口径；IQC「落料剪」；「本次资料未载明」状态标注；经营目标数字与产能口径说明（「不是产能数据。」）；正文 2.1 中的「园区提供整层空间、租金几乎不收并有产业孵化支持」——用户删除的是表1 调研地点单元格里的**地址解释性括注**，不是这段业务事实。

**规则与表述分离**：被删的元说明所对应的**行为约束仍然有效**（不推断人名、不推算产能、MECE 不重复、不写工商全称），只是不得把这些约束写成报告里的自述句。

### 5.7 附录与自检清单规则
- 附录仅保留「附：术语约定（不编章号）」一张表；**不输出证据索引、编制说明、资料清单、改稿记录**。
- 文末「文末自检清单」固定 **7 条（1）—（7）**，措辞随实际交付状态同步，不得引用已删除的附录或证据编号。7 条主题：结构对齐 / 证据可追溯 / 零编造数字 / 编号连续 / 部门不重复 / 无占位符 / 行动计划含责任人与时间。逐条原文见 `references/报告结构规范.md`。

## 六、输出成果结构

```
XX MES 系统建设现场调研报告_YYYYMMDD.docx   ← 唯一交付件（单文件，无外部依赖）
```
文档内部顺序（基线件实测）：
1. 封面标题：`XX MES 系统建设现场调研报告`
2. 「调研结论摘要」+ 5 条
3. 一、项目基本信息 → 本章结论 → 表1（2 列 × 9 行 = 表头 + 8 字段）
4. 二、项目背景 → 本章结论 → 2.1 公司背景（表2，5 列）/ 2.2 主要产品（表3，3 列）/ 2.3 主要工艺流程（「来料→…→出货」全流向 + 关键工序特点）
5. 三、项目调研 → 本章结论 → 3.1—3.11 共 11 个三段式子节（表4 / 表5 / 表6 分列于 3.2 / 3.8 / 3.9）
6. 四、实施范围与边界建议 → 本章结论 → 4.1 业务与系统范围 / 4.2 边界与前提
7. 五、后续行动计划 → 本章结论 → 表7（3 列 × 14 行 = 表头 + 13 条待办）+ 表注
8. 附：术语约定（不编章号）→ 1 张表
9. 文末自检清单 → 7 条
10. 页脚：编制：摩尔元数 MOM 售前顾问组｜编制日期：YYYY-MM-DD｜版本：V1.0｜第 N 页（PAGE 字段）

**表格总数 = 8**（7 主表 + 1 附录术语表）。可直接复制的章节与表头骨架见 `assets/报告章节骨架.md`。

## 七、命名与版本要求

| 项 | 规则 |
|---|---|
| 文件名 | `<客户简称> MES 系统建设现场调研报告_<YYYYMMDD>.docx`；`YYYYMMDD` 用**编制日期**（非调研日期）。客户简称取项目目录名或用户指定，**不擅自补「有限公司」** |
| 修订版 | 仅当原文件被 WPS/Word 独占无法回写，或用户明确要保留历史版本时，追加 `_修订版.docx`；正常情况直接写回原文件名 |
| 版本号 | 页脚 `V1.0` 起；每次实质性修订按 `V1.1`、`V1.2` 递增，或按用户指定 |
| 页脚日期 | 与文件名 `YYYYMMDD` 一致，格式 `YYYY-MM-DD` |
| 页脚四要素 | 编制单位 / 编制日期 / 版本 / 页码，**缺一不可**；不得含「依据：…」等资料来源字段 |
| 备份 | 改前备份到系统 Temp，命名 `<报告名>_<修改事由>前备份.docx`；交付目录只留成品，中间脚本/文本一律清理 |

## 八、验收标准

交付前运行 `scripts/verify_report.py <docx路径>`，全部检查项 PASS 方可交付。10 类检查：

1. **结构**：五章齐全且编号连续；2.1—2.3、3.1—3.11、4.1—4.2 连续；「调研结论摘要」5 条。
2. **三段式**：11 个子节各有「现状：/ 需求：/ 痛点：」段首结论句。
3. **表格**：恰好 8 张表；表1—表7 表头字段与范本一致；表7 每条待办责任人与时间非空。
