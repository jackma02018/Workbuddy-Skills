# 摩尔方案-需求与改善方向

## 一、这个技能解决什么

售前最常见的失败不是"写得不好看"，而是**内容不可追溯**：改善方向凭经验拍脑袋，评审时客户问"这条依据是什么"答不上来；或者需求照抄客户原话，没做归类与优先级，5 个模块平铺看不出主次。

本技能强制一条链路，产出的每一句改善方向都能回溯到具体需求与依据：

```
业务需求（客户原话+事实） → 当前痛点（可量化的现状） → 根因（机制层面） → 改善方向（含思维方式） → 方案价值（可验证指标）
```

## 二、触发条件

**命中任一即触发：**
- "整理客户需求 / 梳理需求 / 输出需求清单"
- "给改善方向 / 改善建议 / 优化方向 / 解决方案方向"
- "按模块给 MES / MOM 建议"（计划、仓库、生产、品质、设备、工艺、物料等任一模块）
- "把会议纪要 / 调研记录 / 录音转写 / 微信对话整理成方案"
- "生成方案初稿 / 需求与改善方向文档"

**不触发（移交其他技能）：**
- 已有 PPT 只想改样式/合并/美化 → `摩尔多页PPT合并`、`ppt-polish`、`more-jpg-to-ppt`
- 已有成品文档要套 Word 模板 → `moore-temp-to-doc`
- 只要一份调研计划表格 → `tencent-docs-sheet-generation`
- 要做完整 MES 方案（含版式设计、图标、栅格） → `摩尔结构化方案编写`

## 三、输入参数

| 参数 | 必填 | 说明 | 缺省处理 |
|---|---|---|---|
| `source_path` | 是 | 资料文件夹 / 文档 / 图片路径 | 无 → 先向用户索取，不得凭空编造 |
| `customer` | 是 | 客户简称，用于标题与文件名（如"江阴旺达电子"） | 从资料或路径推断，并显式回告推断结果 |
| `modules` | 否 | 模块顺序，默认 `生产计划/仓库/生产/品质/设备` | 按客户原话顺序优先，其次按此默认序 |
| `deliverable` | 否 | `ppt`（默认）/ `docx` / `html` / `md` | ppt |
| `template` | 否 | 摩尔模板路径，默认 `E:\02跟进项目\摩尔方案模板.potx` | 文件不存在 → 先报告并询问 |
| `date_prefix` | 否 | 文件名前缀，默认取当天 `YYYYMMDD` | — |
| `unknown_policy` | 否 | `mark`（默认，标"待确认"）/ `ask`（停下来追问） | mark |
| `depth` | 否 | `standard`（默认，每模块 3-5 条）/ `deep`（每模块 5-8 条 + 根因分析） | standard |

## 四、执行步骤（六阶段）

### 阶段 1｜需求接收与澄清
- **输入**：客户原始表达（口语、微信、纪要）。
- **动作**：只做两件事——① 逐句拆成原子需求条目；② 标出**歧义词**（"物料齐套""产能不够""追溯难"这类主观词）。
- **输出**：原子需求条目清单，每条带 `来源`（哪份资料/第几句）。
- **判断标准**：每条需求都能回答"这是客户说的，还是我们推测的？"推测的必须打标。
- **❌ 常见错误**：一收到就开始想方案，把"想要的"和"需要的"混为一谈。

### 阶段 2｜信息收集与整理
- **输入**：`source_path` 下全部资料。
- **动作**：**完整读取，不抽样**。docx/txt 直接抽文本；xlsx 逐 sheet 读；图片逐张读（现场照片、设备铭牌、看板照片是重要事实来源）。
- **输出**：事实卡片清单，按四类归档：
  - `背景`（行业、产品、客户规模、组织）
  - `产品与工艺`（工序路线、节拍、特殊工艺）
  - `规模基线`（产线数、日产能、仓面积、人员）
  - `现状与管理`（现有系统、竞品、已上过的系统、硬件）
- **判断标准**：每条事实带数值或原句，**不带形容词**。"管理比较混乱"不是事实，"成品仓 1 人管 500㎡、账实不符"才是。
- **❌ 常见错误**：只看主文档，跳过 xlsx 和照片；把客户自述的痛点当事实直接抄。

### 阶段 3｜缺失信息追问
- **输入**：事实卡片 + 原子需求。
- **动作**：按对方案影响面排序，识别**致命缺失**（不知道就没法定方案）与**可假设缺失**。
- **输出**：待确认清单，每条写 `问题 / 为什么重要 / 建议默认值`。
- **判断标准**：
  - 致命缺失 → 必须问用户（例：工序节拍不明，无法判断瓶颈）
  - 可假设缺失 → 按行业常规假设 + 标注"待确认"，**不阻塞进度**
- **❌ 常见错误**：因为缺一个次要数据就停下来问 20 个问题；或相反，把致命缺失也自己脑补。

### 阶段 4｜需求归类与优先级判断
- **输入**：事实卡片 + 原子需求 + 待确认清单。
- **动作**：
  1. 归入模块（计划/仓库/生产/品质/设备/工艺/物料/…），**同一事实只归一个主模块**，避免重复。
  2. 打优先级，维度三选：`业务价值 × 落地难度 × 客户关注度`。
  3. 标注**改善类型**：`卡控类`（流程型）/ `数据类`（数据驱动）/ `标准类` / `协同类` / `设备类`。
- **输出**：模块矩阵（模块 / 痛点数 / 优先级 / 改善类型）。
- **判断标准**：优先级必须**显式给理由**（"客户 3 次提到 + 涉及 8 条线 + 竞品已具备"），不许只写 P0。
- **❌ 常见错误**：所有模块都标 P0（等于没排）；按客户提问顺序排（那是他的关注顺序，不是实施顺序）。

### 阶段 5｜方案方向与改善建议输出
- **输入**：模块矩阵。
- **动作**：对每个模块，用四层链路成稿——
  1. **业务需求**：客户要达成什么（用他的语言）
  2. **当前痛点**：现状 + 量化后果（必须带基线数字）
  3. **改善方向**：具体做法，**必须给两个视角**
     - 视角 A（流程型思维）：带卡控点 / 状态机 / 触发条件
     - 视角 B（系统 / 数据驱动 / 标准化 / 供应链协同 / 设备全生命周期，任选其一切合）
  4. **方案价值**：可验证指标（有基线才能给目标）
- **思维方式标注**：每模块标一个思维类型，**相邻模块不重复**，全套覆盖 `系统思维 / 数据驱动思维 / 精益思维`。
- **判断标准**：改善方向必须能被检验——"建立批次绑定关系并在投料扫码处卡控"✅；"加强物料管理"❌。
- **❌ 常见错误**（本次项目最典型的三个坑）：
  - 只给一个视角，方案厚度不够，评审显得单薄
  - 改善方向与痛点不对应（痛点讲排产慢，方向讲仓库账实）
  - 价值句全是"提升效率、降低成本"这类无基线空话

### 阶段 6｜文档版本命名与归档
- **输入**：定稿内容 + 交付格式。
- **动作**：按下方命名规则生成文件名，落到**源资料同目录**（不新建目录）。
- **判断标准**：文件名能被第三个人一眼看懂是什么、哪天的、哪个版本。

## 五、输出格式（固定结构与章节顺序）

方案类文档**必须**按此顺序，章节不得增删调序：

```
封面/标题：{客户名} · {行业} · {方案类型}
0. 需求概述            ← 阶段1-2 收敛结果：客户背景 + 产品工艺 + 规模基线 + 现状
1. 需求清单与优先级     ← 阶段4 模块矩阵（模块/痛点/优先级/改善类型/依据来源）
2. 改善方向            ← 阶段5 主体，按模块分节，每节四层：业务需求/当前痛点/改善方向(双视角+思维类型)/方案价值
3. 依据说明            ← 每条改善方向挂依据：来源文件、原始事实/原话、数据基线；无依据的条目明确写"行业通用实践"
4. 结论与待确认事项     ← ① 优先级结论与建议实施顺序 ② 待确认清单（问题/为什么重要/建议默认值）
5. 附录（可选）        ← 术语表、现有系统与竞品清单
```

**需求 → 改善方向的推导逻辑（三条硬规则）**

1. **痛点必须带基线**。没有基线数字的痛点不成立，也不能推出可验证的价值。
   `成品仓 1 人管 500㎡ + 账实不符` → `条码/RFID 出入库+周期盘点，账实一致率 ≥ 99%`
2. **每条改善方向必须同时回答"在哪卡"和"靠什么判断"**。只在流程上卡 = 卡控类；靠数据算 = 数据类；靠标准统一 = 标准类。
3. **改善类型 ↔ 思维类型要匹配**，不能随意贴标签。
   `系统思维` → 跨模块打通、主数据/流程体系化；`数据驱动思维` → 采集/实时/预警/看板；`精益思维` → 消除浪费、节拍、TPM、快速换型。

## 六、约束边界

**必须：**
- 数据优先真实。凡未在资料中找到依据的数字，一律标 **「待确认」**，禁止估算后当事实写。
- 行业缩写（SMT / BOM / ERP / FIFO / ECN / Andon / IQC / SPC…）**保留**，属专业内容。
- 页数与顺序严格按客户指定；每页三模块结构不擅自增删。
- 交付前必须做校验并逐项报告（见下）。

**禁止：**
- ❌ 编造规模数据（产线数、产能、人员、面积）——这是本技能最容易翻车的地方。
- ❌ 把"改善方向"写成产品功能清单（写"卡控与追溯"，不写"MES 模块 ABC 功能点"）。
- ❌ 价值句无基线。
- ❌ 未做校验就宣称完成。

**交付门槛校验清单（8 项，全过才算完成）**
1. 文件可正常打开（`zipfile.testzip()` 通过，全部 xml 良构）
2. 图片/Logo 无丢失（`ppt/media/*` 数量与原版一致）
3. 无文字溢出（按实际字号估算行高，不用硬编码）
4. 英文/竖线等残留符号已清理（除非客户要求保留专业缩写）
5. 字体字号全局一致（字体统一，字号按层级——**注意：字面"全部同字号"会导致版式崩溃，须向用户说明并给推荐版**）
6. 待确认项已全部列出、未被隐藏进正文
7. 文件名符合命名规则、落在源资料同目录
8. 若源文件被 WPS/Office 占用（存在 `~$` 锁文件）→ 另存新版本号，**不 kill 用户进程、不强删**

## 七、版本命名与归档规则

```
YYYYMMDD_{客户简称}.pptx                ← 首个交付版
YYYYMMDD_{客户简称}_v2.pptx             ← 第 2 次修订
YYYYMMDD_{客户简称}_v3b.pptx           ← 分叉版本（b = 变体）
YYYYMMDD_{客户简称}_v3b_说明.md        ← 同名说明文件（改动点、为什么这样改）
```

规则：
1. **日期前缀取生成当天**，客户简称用简称不��全称（`江阴旺达电子` 而非 `无锡-江阴旺达电子有限公司`）。
2. **归档到源资料同目录**，不新建文件夹。
3. **推荐版与合规版并存时用字母后缀**，并在同名 `.md` 里写清差异，让用户按场合挑。
4. **源文件被占用时另起版本号**，并在交付说明里交代"关闭后可覆盖回原名"。
5. 一次交付只改一个维度（字体/版式/内容），否则无法回溯是哪次改动引起的效果。

## 八、常见错误总表

| 阶段 | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 接收 | 把"想要的"当"需要的" | 方案跑偏 | 分开记录，推测的必须打标 |
| 收集 | 只读主文档 | 漏掉 xlsx/照片里的关键基线 | 完整读取，逐份登记 |
| 收集 | 抄客户自述痛点当事实 | 未经核实写进方案 | 事实与客户判断分开记 |
| 追问 | 缺一个次要数据就停 | 进度拖延 | 区分致命/可假设，只问致命 |
| 归类 | 全部标 P0 | 看不出主次 | 打分给理由 |
| 归类 | 按客户提问顺序排 | 顺序不是实施顺序 | 按价值×难度×关注度排 |
| 输出 | 只给一个视角 | 方案单薄 | 必给双视角 |
| 输出 | 改善方向不对应痛点 | 逻辑断裂 | 每节写完做一次回指检查 |
| 输出 | 价值句无基线 | 无法验收 | 有基线才给目标 |
| 归档 | 文件名无版本/无日期 | 混乱 | 严格按命名规则 |
| 校验 | 声明完成但未验溢出 | 交付即返工 | 过 8 项门槛清单 |

## 九、最小可复用产物（供快速起步）

一个模块的成稿模板（复制即用）：

```markdown
## {模块名}｜{思维类型徽标}

**业务需求**
- {客户要达成什么，用客户语言，1-2 条，引用真实数据}

**当前痛点**
- {现状描述 + 量化后果，必须带基线数字}
- {第二类痛点}

**改善方向**
- 视角A · 流程型：{具体做法 + 在哪卡控 + 卡控触发条件/状态机}
- 视角B · {数据驱动/系统/标准化/供应链协同/设备全生命周期}：{具体做法 + 靠什么数据或标准支撑}

**方案价值**
- {指标}：{基线值} → {目标值}（{依据}）
- {效率/质量/成本类指标 2-3 条}
```
